# ducknng manifest and method registry

This document is binding for how `ducknng` methods are declared, registered, exposed, deprecated, and removed. The key rule is that the method registry is the server-side source of truth and the manifest is a generated or derived representation of that registry state. In other words, the project should not drift into a model where runtime behavior lives in one place and public capability description lives in another unrelated place.

The manifest exists to tell clients what methods exist, how those methods are named, which transport pattern they use, what payload formats they accept and emit, what schemas they expect and return, whether they are stateless or sessionful, whether they are experimental or deprecated, and which version of the protocol introduced them. The manifest is therefore not just descriptive documentation. It is part of the contract between the server and every client implementation.

The registry must support single-method operations and bulk operations. A single method must be registerable, unregisterable, and discoverable by name. Groups of methods must also be registerable and removable in bulk so that protocol families can be installed coherently instead of piecemeal. That is especially important for families such as core control, unary SQL execution, session queries, and future event-oriented protocols. The presence of bulk registration is not an implementation nicety; it is part of the intended architecture because the project explicitly wants a way to define, add, and remove methods as coherent sets.

Each public method needs a descriptor. The exact C layout may evolve, but the logical content is fixed. A descriptor must carry the method name, its family, a human-readable summary, its transport pattern, its request payload format, its response payload format, its response mode, its request schema declaration, its response schema declaration, its session behavior, whether it is idempotent, whether it is deprecated, and the protocol version in which it was introduced. Experimental status is still a project-level documentation concept for the session family today; once the registry and exported manifest grow an explicit experimental flag, that field should be added there instead of being implied only by prose.

`ducknng_list_methods()` is the SQL projection of that same descriptor state. It exposes auth, session, mutation, idempotence, deprecation, accepted/emitted flags, request/reply limits, schemas, and introduction version; it must not maintain a smaller parallel policy model.

Payload format values should remain small and explicit. A method may declare that it uses no payload, JSON payloads, or Arrow IPC stream payloads. Arrow IPC file payloads are reserved for future use if they ever become necessary, and custom binary payloads are strongly discouraged because they push the project back toward bespoke per-method framing. If a future reply-metadata envelope is ever introduced, it should be negotiated as a generic capability layered above the existing payload-format model rather than mislabeled as a second row codec.

Response modes also need explicit declaration because they determine how a client interprets a successful reply. A method may return no payload, metadata only, rows, either metadata or rows depending on execution, session-opening information, or event-style output in the future. This distinction is especially important for `exec`, which can legitimately return either metadata about a non-row-producing statement or a tabular result when row output is requested.

Session behavior must be declared directly in the method descriptor rather than inferred from implementation details. A method can be stateless, open a session, require an already-open session, close a session, or cancel a session. That declaration matters because it controls both client expectations and how the server organizes its own execution state. A method that is logically sessionful but undocumented as such is a protocol defect.

The manifest should be exported as stable JSON because JSON is the easiest universal interchange format for discovery data across R, Python, Go, JavaScript, and C tooling. It contains server/protocol identity, security and execution policy, session limits, capability summaries, and the method descriptors. The current capability summary names the supported serialization modes, fetch metadata, session schema features, and `parameter_binding`. Parameter binding declares Arrow-struct encoding, positional child-order semantics, the currently registered methods that support it, and the 65,535-parameter limit.

The manifest is discovery and policy metadata, not a live telemetry feed. Dynamic counters such as active pipes, in-flight request count, monitor ring occupancy, and connection churn belong in runtime introspection surfaces such as `ducknng_list_servers()`, `ducknng_list_pipes()`, `ducknng_read_monitor()`, and `ducknng_monitor_status()`. Keeping these out of the manifest makes manifest replies stable enough for cache/equality tests and avoids mixing capability negotiation with transient load state.

The current stable execution metadata is intentionally small. `server.execution.model` reports the configured service-side DuckDB execution model: `shared_serialized_connection`, `service_serialized_connection`, or `request_connection`. That is capability and policy metadata, not transient telemetry, so it belongs in the manifest as well as `ducknng_list_servers()`.

Local SQL client helpers that do not name a server method are not manifest entries. This matters for the aio surface and for transport adapters. `ducknng_request_raw_aio(...)`, `ducknng_request_socket_raw_aio(...)`, `ducknng_get_rpc_manifest_raw_aio(...)`, `ducknng_run_rpc_raw_aio(...)`, `ducknng_send_socket_raw_aio(...)`, `ducknng_recv_socket_raw_aio(...)`, `ducknng_ncurl_aio(...)`, `ducknng_ncurl_stream_open_aio(...)`, `ducknng_ncurl_stream_recv_aio(...)`, `ducknng_ncurl_stream_close(...)`, `ducknng_aio_ready(...)`, `ducknng_aio_wait(...)`, `ducknng_aio_collect(...)`, `ducknng_aio_collect_decoded(...)`, `ducknng_ncurl_aio_collect(...)`, `ducknng_ncurl_stream_open_aio_collect(...)`, `ducknng_ncurl_stream_recv_aio_collect(...)`, `ducknng_aio_cancel(...)`, `ducknng_aio_drop(...)`, `ducknng_ncurl(...)`, and the scalar frame accessors (`ducknng_frame_version(...)`, `ducknng_frame_type(...)`, `ducknng_frame_status(...)`, `ducknng_frame_flags(...)`, `ducknng_frame_type_name(...)`, `ducknng_frame_name(...)`, `ducknng_frame_payload(...)`, `ducknng_frame_payload_text(...)`, `ducknng_frame_error_text(...)`, `ducknng_frame_end_of_stream(...)`) are runtime-local client or transport helpers over ordinary declared methods, not registry methods exported by the server. The same is true for the HTTP route helpers `ducknng_register_http_route(...)`, `ducknng_register_http_route_pattern(...)`, `ducknng_unregister_http_route(...)`, `ducknng_unregister_http_route_pattern(...)`, `ducknng_list_http_routes()`, `ducknng_http_request()`, `ducknng_http_request_body()`, the outbound HTTP profile helpers `ducknng_register_http_profile(...)`, `ducknng_drop_http_profile(...)`, `ducknng_list_http_profiles()`, the named request accessors, the strict header/query/cookie/path parser helpers, and the one-row response-builder macros: they configure or inspect the local HTTP service/client layer, but they do not add manifest-derived RPC methods. The manifest should continue to describe the underlying methods and frame contracts, while those helpers remain local ergonomics layered on top.

The implemented HTTP/HTTPS carrier therefore does not create a second manifest namespace. The same descriptors for `manifest`, `handshake`, `query_prepare`, `exec`, `query_open`, `fetch`, `close`, and `cancel` remain authoritative regardless of carrier. `docs/http.md` pins frame-over-HTTP rather than a second method namespace.

For the session query family, the manifest must be concrete enough that a client can implement the lifecycle without reading server source. `query_open` declares one opened session, JSON session metadata, and optional correlation, batch, serialization, and parameter-tuple request fields. `fetch` requires the session id and token and may emit Arrow IPC, `ducknng_quack_batch`, or JSON terminal metadata. `close` and `cancel` consume the same owner proof and emit control metadata only. `query_open` also declares `mutates_state = true`: the session path accepts DuckDB SQL and is not a hidden read-only alternative to `exec`.

A method schema declaration is normative for clients. `exec` takes one Arrow row containing `sql`, `want_result`, and optional `params`; it returns metadata or rows. `query_open` and `query_prepare` use the same optional positional parameter struct. `query_prepare` is stateless, non-mutating, accepts exactly one statement, and returns a zero-row Arrow stream carrying the result schema. `fetch`, `close`, and `cancel` use JSON session control. Transport-derived identity remains request context rather than a payload field. A manifest/implementation mismatch is an implementation defect.

Method names are grouped into stable families. The control family includes `manifest` and `handshake`; the query family includes stateless `query_prepare` plus the `query_open`/`fetch`/`close`/`cancel` lifecycle; `exec` is an opt-in SQL method. Reserved names such as `server_info` are not implemented until they appear in the registry and exported manifest.

Adding a method requires a descriptor, registry integration, manifest exposure, schema declaration, and tests. Removing a method should normally proceed through deprecation unless the method was explicitly experimental. Deprecation itself must be visible in the manifest so clients can warn or adapt cleanly. This is especially important once external clients begin to rely on the server contract in a more stable way.

Bulk registration should be the normal way to install method families. The registry should be able to register a core control bundle, a core execution bundle, a session-query bundle, and future optional bundles such as experimental features or pub/sub event capabilities. This model makes it possible to enable or disable coherent surfaces rather than sprinkle individual methods throughout startup logic.

The manifest and registry together are the practical implementation checklist for the public RPC surface. A method should not be considered part of `ducknng` until its descriptor exists, the registry knows about it, the manifest exports it, its request and response schemas are declared, its session behavior is documented, and its versioning status is explicit. Descriptor `requires_auth` is enforced against verified transport-derived caller identity when present; listener policy may also require mTLS identity before any method dispatch. For the query family specifically, the manifest is incomplete unless it also states the session state transitions, `session_token` ownership requirement, server-owned effective idle timeout, optional mTLS owner-identity binding, idempotency of `close`, best-effort semantics of `cancel`, and the temporary REQ/REP constraint that all row delivery happens only on explicit `fetch` replies. That is the rule that keeps the project extensible without becoming shapeless.
